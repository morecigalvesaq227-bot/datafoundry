# Agent 项目学习记录：从请求到工具调用

> 日期：2026-11-18  
> 这份笔记整理了今天的代码导读和交流，便于之后按真实代码继续学习；不是完整聊天记录。示例与说明均做了通用化处理，不包含真实客户工单、内部服务地址、密钥、业务数据库或本地向量库。

## 今天建立的整体认识

客户答疑助手不是“一个模型加一个聊天框”，而是应用在 Agent 框架之上，围绕实际业务接入认证、上下文、检索工具、数据访问策略、前端交互和运行记录等模块。模型负责理解问题、决定下一步以及组织语言；权限判断、参数校验和实际数据访问由应用代码与工具完成。

可以先用这条主线理解一次问答：

`用户输入 → Web 前端 → API/Agent 运行时 → 模型判断 → 工具执行（需要时）→ 工具结果返回模型 → 答案与运行事件回到前端`

## 代码结构地图（学习入口）

以下是今天沿代码梳理出的关键边界，文件位置可能随版本演进，应以当前分支为准：

- `apps/web`：工作台页面、会话交互与前端 API 代理。
  - `apps/web/src/app/data-tasks/data-tasks-app.tsx`：发送问题并启动 Agent run 的前端入口。
  - `apps/web/src/lib/api-proxy.ts`：把浏览器请求转交给 API 服务，并处理流式响应。
- `apps/api`：HTTP/API 入口、身份与工作区上下文衔接、一次运行的组装。
  - `apps/api/src/server.ts`：接收 Agent 请求，整理用户、会话和 run 信息。
  - `apps/api/src/run-agent-assembly.ts`：组装规范化运行上下文和 Agent。
- `packages/agent-runtime`：模型、工具和 Agent 执行策略的核心边界。
  - `packages/agent-runtime/src/index.ts`：按运行上下文装配 Agent 和可用工具。
  - `packages/agent-runtime/src/tools/support-evidence.ts`：客户答疑证据检索工具的定义与执行入口。
  - `packages/agent-runtime/src/tools/governed-tool-factory.ts`：在工具调用外层实施调用约束、结果整理和错误/事件处理。

## 一次请求是怎样走完的

1. 用户在 Web 输入问题，前端发起一次 run。会话标识用于关联同一段对话；run 标识用于标记这一次执行。
2. API 结合已认证身份、工作区和启用资源创建运行上下文。身份与范围不能由模型自行指定。
3. Agent runtime 把模型配置、上下文和策略允许的工具交给 Agent 框架（项目使用 Mastra 作为运行时组成部分）。
4. 模型可能直接回答，也可能提出一个带参数的工具调用。提出调用不等于工具已经执行。
5. 应用校验工具是否可用、参数是否符合 schema 和策略限制，再由工具代码访问受控资源。
6. 工具结果返回给模型继续生成；事件和结果以流式方式送回界面，并可供运行记录/Trace 查看。

关键安全边界：模型不会因为“知道某个数据库”就直接访问它；真正的访问发生在经过授权和校验的服务端工具代码中。

## Mastra、Agent 与工具分别是什么

- LLM/模型：负责语言理解、生成和选择下一步；它不是数据库，也不是整个 Agent 应用。
- Agent：把模型、提示、工具、运行上下文和控制逻辑组合成一个可执行单元。
- 工具（tool）：由应用定义的、有明确输入输出边界的函数。模型可以请求调用，但执行权和权限仍在服务端。
- Mastra：Agent 开发与运行框架，提供组织 Agent/工具及执行流程的机制；它不是某个模型，也不替代产品自己的认证、业务规则或数据服务。
- DataFoundry 应用层：把框架能力接到工作台、身份/工作区、资源配置、审计和具体业务工具上。

因此，“基于框架搭建 Agent”更像是：框架提供运行骨架，产品代码定义 Agent 能做什么、对谁做、能访问哪些数据，以及如何留下可检查的证据。

## 客户答疑 RAG 在链路中的位置

RAG 不是模型“脑内自带的知识库”，而是 Agent 可调用的一项检索能力。客户答疑场景由证据检索工具找到相关材料，再将受控的检索结果交给模型组织回答。检索索引、向量化与检索策略属于检索层；工具的权限、输入校验和执行则属于 Agent/runtime 的工具层。

今天的架构讨论还区分了：

- 向量检索：按问题与知识切片的语义相似度寻找候选证据。
- 实体条件优先：问题明确出现表号、字段号、指标号等精确实体时，才用精确匹配补充或优先处理；不是每个普通问题都强制混合关键词分数。
- 检索不等于答案正确：要分别评估候选召回、证据质量、最终回答和线上处理效果。

## 后续学习路线

1. 跟读一次请求：从前端提交、API 接收，到 Agent run 建立。
2. 跟读模型接入：配置如何解析、模型如何被 runtime 调用、流式事件如何返回。
3. 跟读工具：以 `search_support_evidence` 为例，理解 schema、授权、执行、错误与结果。
4. 学记忆与隔离：区分用户、工作区、session、run；逐一确认数据键、授权边界和生命周期。
5. 学可观测性与评测：Trace、badcase、离线基准、线上指标分别回答什么问题。
6. 最后回看部署与多用户运行：哪些配置是服务端共享的，哪些状态必须按身份隔离。

建议每一节都用“输入是什么、经过哪些函数、输出/事件是什么、失败时在哪里可见”四个问题来读代码。

## 术语小抄

- **Session**：一段持续对话的标识；通常关联多轮消息。
- **Run**：一次具体的 Agent 执行；同一 session 可有多次 run。
- **Trace**：一次执行过程的可观测记录，可包含步骤、工具调用、耗时与错误。
- **RAG**：检索增强生成；先检索外部证据，再让模型基于证据回答。
- **Schema**：对工具输入/输出结构的约束，帮助在执行前发现不合规参数。
